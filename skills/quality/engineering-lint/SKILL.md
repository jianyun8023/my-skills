# Engineering Lint — 工程规则发现与落地

把项目中已经接受的工程约束转化为可重复执行的检查，让 Agent 不再依赖记忆、Prompt 或人工 Review 反复避免同一种错误。

本技能不是“多装几个 Lint 工具”，而是先理解当前项目，再判断哪些约束值得机械化、现有工具能否表达、怎样避免误报，以及如何让 CI 阻止新问题回流。

## 适用场景

- 为当前仓库建立或完善 Lint、静态分析和架构规则。
- 项目存在反复出现的 Agent 错误、代码坏模式或架构边界漂移。
- 希望将 AGENTS.md、架构文档、设计约束转成自动检查。
- 评估现有工具是否足够，或是否需要 ast-grep、自定义 Detekt/Clippy 规则等。
- 清理已有违规、建立历史基线并接入 CI。
- 对已有规则检查误报、漏报、覆盖范围和维护成本。

## 不适用

- 只需要修复一个普通代码缺陷，且没有规则治理诉求。
- 只做格式化或一次性代码风格统一。
- 没有证据地要求所有语言、模块都增加同一套工具。
- 以 Lint 代替单元测试、集成测试、运行时验证或安全审计。
- 未经用户要求就执行全仓大规模重构、发布、推送或修改分支保护。

## 调用方式

支持自然语言，也支持以下明确模式：

| 调用 | 行为 |
| --- | --- |
| `engineering-lint audit` | 只读审计，输出工具现状、规则缺口和优先级建议 |
| `engineering-lint implement` | 实施本次授权范围内的规则、修复、测试和 CI 接入 |
| `engineering-lint verify` | 验证规则的正反例、误报、基线和 CI 接线 |
| `engineering-lint update` | 根据新出现的重复问题补充或调整规则 |

未指定模式时，根据用户动词判断：审查/调研/盘点按只读 audit；明确要求增加、落地、优化、接入或修复时进入 implement。不要把一次 audit 自动扩大成全仓重构。

## 核心原则

1. **项目事实优先**：先读当前仓库的架构文档、AGENTS.md、构建配置、CI 和已有规则。文档与源码冲突时核实实际实现，并保留未解决差异。
2. **现有工具优先**：先盘点项目已有能力。优先扩展已有工具，不重复引入功能重叠的 Linter。
3. **规则先于工具**：先描述需要保护的不变量，再选择工具。不要因为某工具流行就为它寻找使用场景。
4. **高信号优先**：优先阻断确定性 Bug、已接受的架构边界和反复出现的坏模式。主观风格规则默认 Warning 或不启用。
5. **错误反馈面向 Agent**：规则必须说明违反了什么、为什么不允许、应该如何修复；不要只输出“禁止使用某 API”。
6. **渐进治理**：区分历史问题和新增问题。先建立可解释的基线，再阻断新增违规，逐步偿还历史债务。
7. **规则必须可测试**：每条自定义规则都要有违规、合法和边界样例，防止规则本身退化。
8. **最小依赖**：只有现有工具无法可靠表达约束时，才新增工具或编写自定义规则。
9. **证据分级**：区分已证实缺陷、违反明确约束、维护性建议和待验证假设，不把代码气味说成确定 Bug。
10. **不改变产品语义**：规则治理和历史清理默认不改变产品行为；需要行为变更时单独说明并验证。

## 快速工作流

### 1. 确定范围和当前状态

- 确认仓库根目录、当前分支、工作区是否有未提交修改；不得覆盖用户已有改动。
- 读取项目说明、AGENTS.md、架构文档、模块边界、构建文件、依赖锁文件和 CI workflow。
- 识别生产代码、测试代码、生成代码、vendored 代码和平台专属目录。
- 先做与任务相关的代表性检索；只有发现具体风险或规则覆盖缺口时才扩大范围。
- 对大型仓库避免无目标地扫描所有文件或输出海量匹配结果。

### 2. 盘点已有工具

记录每种语言、模块当前已有的：

- 格式化器与编译器检查。
- Lint / 静态分析 / 类型检查。
- 架构与依赖边界检查。
- 安全、依赖漏洞和许可证检查。
- 测试、覆盖率和 CI required checks。
- 基线、忽略项、抑制注解及其维护方式。

检查工具实际执行的目录、source set、构建变体和 CI job。配置文件存在不代表检查已经运行；CI 运行也不代表它覆盖了所有生产模块。

### 3. 发现候选规则

从以下证据寻找规则，而不是凭空制定规范：

- 已发生的缺陷、重复修复、Review 反复指出的问题。
- 架构文档中明确的唯一所有者、依赖方向、线程边界和平台约束。
- 生产代码中可识别的危险 API、资源管理方式和不安全模式。
- Agent 经常复制的坏模式、临时补丁或错误兼容层。
- CI 当前没有覆盖、但项目已明确要求保护的契约。

将候选分为：

- **Correctness / Safety**：可能造成错误、崩溃、泄漏、竞态或安全问题。
- **Architecture**：模块依赖、职责归属、唯一状态所有者、API 边界。
- **Reliability / Lifecycle**：线程、取消、关闭、资源释放和失败路径。
- **Performance**：有具体机制或测量证据支持的高成本模式。
- **Consistency**：格式、命名和风格；默认低于正确性与架构规则。

### 4. 判断是否值得自动化

每条候选规则都回答：

- 规则保护的具体不变量是什么？
- 它是否已被项目接受，或有重复问题作为依据？
- 能否由 AST、类型、依赖图、编译器或测试确定性判断？
- 现有工具能否表达？是否已有等价检查？
- 误报会怎样影响 Agent 和开发者？
- 规则适用哪些目录、语言、source set 和例外？
- 是否能给出清晰的修复指引？
- 规则维护成本是否低于反复人工纠正的成本？

不能稳定自动判定的语义问题，不要伪装成精确 Lint。可以使用契约测试、人工 Review checklist 或文档约束，并明确其自动化边界。

### 5. 选择最合适的执行机制

按以下顺序评估：

1. 编译器、类型系统或语言内建检查。
2. 项目已经使用的 Lint / 静态分析工具。
3. 现有架构测试、依赖分析或构建插件。
4. AST 模式工具（例如 ast-grep、Semgrep）。
5. 现有 Linter 的自定义规则扩展。
6. 独立自定义脚本或专用 Lint 框架。

文本 grep 只用于简单、稳定且不会被注释、字符串、格式变化轻易误判的检查。涉及语法、作用域、类型、导入或调用关系时，优先使用 AST 或类型信息。

具体工具与语言选择见 [工具选型参考](reference.md)。

### 6. 设计规则并实现

每条规则至少定义：

- 唯一 ID、名称、类别、严重级别和适用范围。
- 违规判定逻辑与明确排除项。
- 为什么违反规则、可能造成什么后果。
- Agent 应采取的修复方向。
- 正常样例、违规样例和边界样例。
- 负责人或规则来源，以及必要的迁移说明。

使用 [规则模板](templates/rule-template.yml)。错误信息应当可操作，例如：

```text
ARCH-001: Kotlin production code duplicates Rust-owned
session recovery decisions.

Reason:
Rust is the single owner of recovery policy. A second
implementation can diverge under mixed failure sequences.

Fix:
Keep platform scheduling and Android callbacks in Kotlin;
move the decision to the existing Rust owner and expose
the result through the established bridge.

Allowed:
Independent test reference implementations in test sources.
```

不要仅仅告诉 Agent “不要这样做”；应说明正确的责任归属和可用接口。

### 7. 清理历史问题并接入 CI

- 先运行现有规则，记录历史违规数量、路径和类别。
- 能直接修复且范围明确时，分批清理；不要借机重写无关代码。
- 对暂时无法清理的存量问题建立最小、可审计的 baseline。
- CI 只阻断新增违规；baseline 不得成为无限扩大的豁免清单。
- 每条豁免尽量局部化，附具体理由和范围；禁止宽泛关闭整组规则掩盖新问题。
- 在 CI 中固定工具版本，缓存可复用依赖，上传有价值的报告。
- 将真正需要保护的检查纳入 required check；耗时或不稳定的报告任务可先非阻断。
- 更新本地运行说明和项目规则索引。

### 8. 验证规则自身

至少验证：

- 合法代码不触发（positive / allowed fixture）。
- 违规代码触发预期规则 ID 和信息（negative fixture）。
- 相似但合法的代码不触发（near-miss fixture）。
- 测试代码、生成代码、vendored 代码和例外范围符合预期。
- 本地命令和 CI 使用相同配置、版本和目标目录。
- baseline 只过滤已知存量，不会屏蔽新增问题。
- 修复规则后，相关测试与构建仍通过。

规则没有正反例测试时，不应将自定义规则作为强制门禁。

## 规则分级与上线策略

| 级别 | 含义 | 默认策略 |
| --- | --- | --- |
| P0 / Error | 已证实高风险或违反核心架构不变量 | 修复后阻断新增违规 |
| P1 / Error | 重要可靠性、生命周期或安全约束 | 有可靠检测和低误报后阻断 |
| P2 / Warning | 维护性、性能风险或尚未完全验证的约束 | 先观察、收集误报 |
| Info | 风格建议、迁移提示或可选优化 | 不阻断 |

不要仅为追求零 Warning 而牺牲信噪比。升级规则级别必须有依据。

## 输出要求

### audit

给出：
1. 审计范围、分支和证据来源。
2. 现有工具及其真实覆盖范围。
3. 候选规则：ID、问题、证据、推荐机制、误报风险、优先级。
4. 可以复用的现有能力和不建议引入的工具。
5. 分阶段实施建议。

### implement

给出：
1. 新增/修改文件及每项规则的目的。
2. 使用的现有工具、新依赖及选择理由。
3. 历史问题处理和 baseline 策略。
4. 规则测试的合法/违规/边界结果。
5. 本地验证与 CI 状态；未运行的检查明确标注。
6. 剩余风险、未覆盖范围和后续优先级。

### verify

逐项检查规则能否命中目标、是否误伤合法代码、例外是否过宽、CI 是否真正执行、baseline 是否正确，以及文档是否与配置一致。

## Checklist

审计前：
- [ ] 确认当前分支、工作区改动和用户指定范围。
- [ ] 阅读项目架构规则和 Agent 指令。
- [ ] 盘点已有工具、版本、覆盖路径和 CI。
- [ ] 以实际问题和明确不变量提出候选规则。

实施时：
- [ ] 先复用已有工具，不重复引入同类工具。
- [ ] 每条规则都有理由、修复建议、范围和例外。
- [ ] 自定义规则有合法、违规和边界测试。
- [ ] 基线只处理存量问题，新增违规仍然失败。
- [ ] 不顺手修改产品逻辑或扩大重构范围。
- [ ] 将检查接入与本地一致的 CI required check。

交付前：
- [ ] 验证规则本身和受影响构建/测试。
- [ ] 检查 CI 是否覆盖实际生产模块。
- [ ] 说明未验证项、误报风险和技术债。
- [ ] 更新项目规则文档和运行说明。

## 常见错误

| 错误做法 | 正确做法 |
| --- | --- |
| 一开始就安装多个热门 Lint 工具 | 先定义规则，再选一个能可靠表达它的工具 |
| 只在 AGENTS.md 写“禁止” | 对确定性约束增加可执行检查 |
| 用 grep 判断复杂语法和依赖关系 | 使用 AST、类型信息或依赖图 |
| 一次性打开所有严格规则 | 先测基线，阻断新增问题，再逐步收敛 |
| 为了 CI 变绿而大量 suppress | 修复根因，必要例外局部且有理由 |
| Lint 错误只写 API 名称 | 写明原因、责任边界和正确修复方式 |
| 把代码气味直接定为 P0 | 区分事实、推断、建议和待验证假设 |
| 用 Lint 代替测试或实车验证 | 为动态行为保留相应测试和运行验证 |
| 把规则写死到一个项目 | 通用 Skill 只定义方法；项目规则留在项目仓库 |
| 无关地重构历史代码 | 只清理与已选规则相关的违规，保持变更局部 |
