# Component Governance — 组件与架构治理

让共同变化的能力有明确的维护位置，让调用方只理解必要的接口，让后续改动继续遵守边界。组件可以是 View、hook/controller、函数、业务模块或包；按责任判断，不把它们全部放进一个共享层。

## 适用范围与推进

- 用户本次范围优先。沿用项目已接受的架构、目录、命名、组件库和兼容策略；用当前实现与测试核实。发现冲突说明差异，不以另一项目的约定替换当前契约。
- 实现请求在证据足够后继续修改、迁移和验证；审查请求只交付有依据的建议。技能不额外要求逐步确认，也不授权无关重构、跨仓库写入、发布或后台定时审计。
- 普通改动围绕当前 diff、调用方和反向依赖取证。专项治理从代表路径和实际维护痛点开始，有未解问题再扩展；不默认全仓扫描。证据已足以支持取舍后停止扩查，不以补齐目录或模块数量为目标。
- 使用项目现有工具链。查框架/API 文档时优先 Context7 并核对版本；不可用时说明缺口并查官方来源。本地事实不靠框架惯例推断。

## 审查证据与优先级

- 对候选沿实际消费者追踪状态所有者和生命周期；涉及异步或状态搬迁时，核对父级挂载/重置、订阅、取消与提交路径。文件名、目录位置或单段代码不能单独证明越界或竞态。
- 区分已证实的缺陷/违规、维护性改进、预防性门禁建议和待验证假设。缺陷给出成立的触发条件与后果，越界指明违反的项目规则及依赖路径；证据不足时降低断言强度。静态依赖不等于实测包体或性能影响，门禁通过只说明其覆盖的规则通过。
- 按当前影响、证据强度和改造成本排序。建议提取前比较保留现状、局部修复和调整边界的净收益；审查不要求每一类都有发现，也不为充实报告提出重构。

## 判断是否值得抽取

先看现有能力能否直接复用或小幅扩展，再决定保留局部实现、抽取、调整边界或合并碎片。检查真实调用方及其变化原因：

- **共同语义**：几个实现是否表达同一责任、遵守相同不变量、通常一起变化？外观或代码形状相似不足以证明应共享。
- **接口收益**：调用方是否少了解了状态、顺序、异常和配置？只有转发、改名或透传大量内部参数的包装通常没有收益；有实际协议转换或策略约束的适配器可以很薄。
- **真实变化点**：组合、回调、trait/protocol 或配置解决了什么现有差异？不为想象中的第二个实现建立插件系统、工厂链或万能基类。
- **维护局部性**：一次修复能否集中在责任所有者，还是迫使更多调用方同步修改？删除该抽象后，复杂性是消失了，还是重新散落到调用方？

重复次数、文件长度和函数数量只作线索，不作阈值。单个调用方也可能需要封装复杂生命周期、隔离外部系统或保护不变量；多个调用方也可能因语义不同而应保持独立。若拆分只是增加跳转和透传，就保留或合并实现。

## 确定归属与接口

按现有架构映射下列责任，不要求创建同名目录或凑齐全部层级：

| 责任 | 通常拥有 | 需要留在其他所有者的内容 |
| --- | --- | --- |
| 通用展示与交互 | 样式、布局、焦点、键盘、输入和展示事件 | 具体业务规则、生产服务选择、持久任务 |
| 领域展示与状态 | 业务语义组件、展示转换、领域交互状态 | 其他领域内部实现、重复的业务真相源 |
| 共享机制 | 被实际复用的查询取消、订阅或窗口动作机制 | 领域游标、提交策略、跨领域业务编排 |
| 领域规则与应用用例 | 不变量、状态迁移、业务操作顺序和端口 | UI 框架、平台呈现细节 |
| 基础设施与平台适配 | 网络、存储、系统能力及契约转换 | 上层页面布局和展示状态 |
| 应用装配 | 选择实现、注入依赖、导航及窗口组合 | 被各调用方重复实现的领域规则 |

对本次边界明确几件事即可：谁消费、谁拥有状态、允许哪些依赖、公开什么，以及失败/取消如何表达。

- 依赖方向服从项目规则。跨领域复用经过既定公共接口；通用层不反向认识具体页面或领域。跨领域业务流程交给现有用例/协调者，不借共享 UI 或全局 store 绕过边界。
- 传入实际所需的数据、动作或窄能力。不要为方便把整个 AppModel、全量客户端或容器传下去，也不要只为减少参数额外包一层依赖袋。
- 优先组合既有框架控件。封装应提供明确语义或统一策略，不逐个复制框架 API。复杂模式可用组合、slot/children 或显式变体；`disabled`、`selected` 等单一布尔状态无需机械替换。
- 保持状态的唯一所有者。不要为了复用强制提升全部状态或复制缓存、草稿、任务与保存流程。无头逻辑和视图的拆分需要实际独立消费、生命周期或验证收益。
- 复用异步机制前核对调用契约：查询身份（客户端/连接及影响结果的参数）、取消与迟到响应、刷新完成的等待语义、旧结果保留和交互期间的更新策略。共享 helper 不匹配时比较局部修复与小幅扩展，不为套用它改变调用语义。读取生命周期不接管写入、重试幂等或未知结果恢复。
- 结构调整默认保持既有业务和交互语义，包括空值/未知/失败、选择、焦点、保存顺序及性能特征；必要的行为变化单独说明并验证。

涉及异步复用、状态搬迁、控件/包边界或浅层包装时，按问题读取 [决策示例与来源](references/decision-examples.md) 的对应部分，不必全部加载。

## 落地与持续治理

按任务大小采用必要动作，不把下面的要点当成每次必走的审批流程：

- **定位最小变更**：找到现有实现、代表性调用方、导出与检查入口。重要取舍简述现状问题、目标所有者、接口和受影响消费者；没有收益时明确建议不抽取。
- **完成消费迁移**：实现后更新授权范围内的实际调用方，删除被替代的实现、导出、依赖和独占样式。只新增组件而无人使用不算完成；不要为保留旧内部路径增加无要求的兼容包装。未授权或无法访问的消费者列为剩余工作。
- **核实包边界**：独立包要有实际消费者或明确的构建、依赖隔离、维护/发布收益，工作区内的应用也可构成消费者。检查包声明的公共入口或公开子路径、依赖与宿主版本、构建产物及锁文件；不能靠工作区 alias 或直接引用源码证明发布包可用。类型导出也属于契约。
- **接入现有门禁**：优先扩展项目已有 lint、依赖图、可见性、构建或架构检查。新增规则对应已接受且可执行的约束或已观察到的越界，门禁缺口单列为预防建议。能用语法解析的导入检查不退化为宽泛文本匹配；按语言考虑静态/动态导入、再导出、类型引用和循环，不机械禁止所有依赖或公开子路径。
- **保留决策依据**：更新现有架构或组件文档中的唯一入口、责任和使用示例。影响长期演进且理由不明显的取舍才写 ADR，包括确有必要保留的“不抽取”决定；不强制每个组件写 ADR、建术语表或生成报告。
- **按影响验证**：沿实际 diff 和消费者选择类型/构建、边界检查、相关行为及必要的界面验证。涉及身份、持久化、事务或恢复时保留相应回归。可逆的普通 UI 拆分不逐项新增测试；共享包要验证实际制品消费，内存替身不证明真实适配器正确。

门禁用于已明确且可执行的约束，不能自动判断抽象是否值得；自动化检查和评审共同维护边界。区分本次新增越界和存量问题，局部重构不扩成全仓清理；必要例外应有具体理由和范围，不用宽泛豁免掩盖新违规。验证通过且没有新修改、失败或具体未解风险后停止扩测。

审查交付说明检查范围、关键证据、建议级别和取舍；实现交付补充最终归属、消费者迁移及实际验证结果。保留“不抽取”的有益结论，不强制固定报告模板，不把目录整齐、编译成功或组件数量当成行为等价证据。
